# 眠屿 Mianyu — Sleep Isle

基于生成式 AI 与个性化声景的智能助眠平台。

用户用自然语言说出今晚的状态，AI 给出可解释的助眠方案；用户再像布置房间一样组合雨声、壁炉、故事和呼吸练习，形成属于自己的睡眠空间。

> 本仓库当前以软件设计文档与方案为主。产品不进行疾病诊断或治疗，定位为睡眠习惯管理与情绪放松工具。

组长职责见独立文件：[组长协作指南.md](./组长协作指南.md)。完整项目书见 [眠屿项目书.md](./眠屿项目书.md)。给 Grok 4.6 用的提示词见 [给Grok-4.6的提示词.md](./给Grok-4.6的提示词.md)。

# 项目书（精简）

## 一、项目概述

**眠屿**（英文名 **Mianyu — Sleep Isle**）是面向睡眠困难、压力较大人群的智能助眠软件。核心是：AI 理解用户、用户搭建声景、健康习惯获得正向反馈。

软件本身即可运行，手表、耳机和 VR 仅为可选扩展。产品不做疾病诊断或治疗。

核心理念：睡眠优先、用户可控、低刺激交互、渐进式个性化。

愿景：让用户不必在大量音频里反复试听，而是用自然语言说出当下感受，和 AI 一起创造愿意进入、能够放松的睡眠空间。

## 二、背景与用户

现有助眠应用多为音频列表：筛选成本高、创作空间小，声音、画面和陪伴相互割裂，打卡还容易变成压力。眠屿把「找音频」升级为「可对话、可编辑、可成长的助眠空间」。

目标用户：压力较大的学生和都市青年，以及喜欢白噪音、ASMR、虚拟陪伴或想自己布置空间的人。

典型场景：用户说「今天很累，想听雨声，但不要打雷」。AI 生成「夜雨书房」：窗外小雨、室内壁炉、低音量翻书声，并 30 分钟后渐弱。用户也可进入房间，把雨声放到窗外、故事声放到床边。次日做简短反馈，系统据此优化推荐。

## 三、产品结构与功能

一个岛屿、两个空间、三段流程：室内强调安全感，室外强调自然环境，点击窗户切换；流程为睡前沟通 → 低干扰播放 → 次日反馈。

| 模块            | 说明                                                         |
| --------------- | ------------------------------------------------------------ |
| AI 睡前助手     | 根据情绪、禁忌和时长，在声景、故事、呼吸训练之间给出带理由的建议 |
| AI 睡前故事     | 按主题和音色讲述低刺激故事，结束后只留环境声并渐弱           |
| DIY ASMR 编辑器 | 把声音当作房间里的物体拖放，位置决定远近和左右声道           |
| 室内外场景      | 初始为带窗卧室，点击窗户进入雨夜、海边、森林等               |
| 记录与推荐      | 结合主观反馈和可选设备摘要，并区分「推测」与「测量」         |
| 健康积分        | 奖励稳定作息和有效反馈，不奖励熬夜或刷时长                   |
| 社区分享        | 后续可发布不含私人数据的声景模板                             |

核心流程：选择偏好 → 创建房间 → 与 AI 对话 → 调整方案 → 睡眠模式 → 次日反馈。

## 四、技术框架与 MVP

| 分层     | 方案                                             |
| -------- | ------------------------------------------------ |
| 客户端   | 移动端优先，Flutter 或 React Native              |
| 场景编辑 | 首版二维 / 伪 3D                                 |
| 服务端   | 账号、声景配置、积分、数据同步                   |
| AI 服务  | 大模型输出结构化方案，语音合成讲述，内容审核过滤 |
| 音频引擎 | 多轨混音、空间定位、渐弱、离线播放               |

AI 不直接控制播放器，只输出结构化方案，客户端在白名单内执行。

MVP 只做能证明价值的闭环：室内外二维场景、不少于 12 种声音、拖放混音、AI 文字建议、故事朗读演示、定时渐弱、晨间反馈和基础积分。暂不纳入真实睡眠分期、完整 VR、开放社区和复杂商城。

## 五、边界与安排

隐私上：默认不持续录音、不采集精确健康数据；对话和睡眠信息需单独授权；明确标注非医疗产品。

实施上按 13 周推进：需求与原型 → 视觉交互 → MVP 开发 → 测试 → 答辩。详细章节、页面结构、风险、指标和分工见 [眠屿项目书.md](./眠屿项目书.md)。

# 组员本机协作指南

本文说明组员在自己电脑上如何加入「眠屿」仓库、改文档或写代码、再把改动推回 GitHub。按顺序做即可。

组长看 [组长协作指南.md](./组长协作指南.md)。独立文件版见 [组员本机协作指南.md](./组员本机协作指南.md)。

## 0. 开始前准备

每人都需要：

1. 一个已注册的 [GitHub](https://github.com) 账号
2. 已接受组织邀请，并且对仓库有 **Write** 权限
3. 本机已安装 Git

检查 Git 是否安装成功，在终端执行：

```bash
git --version
```

能看到版本号即可。Windows 可用 [Git for Windows](https://git-scm.com/download/win)，安装后用 **Git Bash** 或 PowerShell。

建议再安装：

- [GitHub Desktop](https://desktop.github.com/)：不熟命令行时可用图形界面
- VS Code 或 Cursor：编辑文档和代码

## 1. 第一次配置（每人只做一次）

把名字和邮箱改成自己的，邮箱尽量与 GitHub 注册邮箱一致：

```bash
git config --global user.name "自己的名字"
git config --global user.email "自己的GitHub邮箱"
```

检查是否写对：

```bash
git config --global --list
```

Windows 上如果中文路径或提交信息乱码，可再执行：

```bash
git config --global core.quotepath false
git config --global core.autocrlf true
```

## 2. 克隆仓库到本机

先向组长要仓库地址。HTTPS 地址形如：

```text
https://github.com/组织名/仓库名.git
```

在自己想放项目的文件夹里打开终端：

```bash
git clone https://github.com/组织名/仓库名.git
cd 仓库名
```

克隆成功后，这个文件夹就是你的工作目录。之后日常改文件都在这里进行。

第一次 `push` 时，GitHub 可能要求登录。推荐用浏览器登录授权，或按 GitHub 提示使用 Personal Access Token，不要把密码写进文件里。

## 3. 日常工作流程

原则：**不要直接在 `main` 上改大内容**。每人建自己的功能分支，改完再合并。

### 3.1 开工前先同步

```bash
git checkout main
git pull origin main
```

确保本地 `main` 和 GitHub 上最新版本一致。

### 3.2 从最新 main 拉出自己的分支

分支名用英文、短、能看懂在做什么：

```bash
git checkout -b feature/requirement-research
```

推荐命名：

| 分支名                         | 用途             |
| ------------------------------ | ---------------- |
| `feature/requirement-research` | 需求分析调研     |
| `feature/architecture-diagram` | 架构图           |
| `docs/project-proposal`        | 项目书或 README  |
| `feature/ui-prototype`         | 界面原型         |
| `fix/typo-readme`              | 改错别字等小修复 |

### 3.3 改文件、查看状态

用编辑器改文档或代码后：

```bash
git status
git diff
```

`status` 看哪些文件变了，`diff` 看具体改了什么。

### 3.4 提交

只添加自己改过、确定要提交的文件：

```bash
git add README.md
git commit -m "补充需求分析调研提纲"
```

一次提交只做一件事。提交说明写清楚「为什么改」，例如：

- `补充室内外场景交互说明`
- `修正 README 中的仓库地址占位符`
- `增加系统总体架构图草稿`

不要提交：

- 自己的账号、Token、`.env`
- 系统缓存、`node_modules`、临时导出文件
- 与任务无关的大体积音频、视频（除非小组约定放入仓库）

### 3.5 推到 GitHub

```bash
git push -u origin feature/requirement-research
```

第一次推这个分支需要 `-u`。之后在同一分支继续改，直接：

```bash
git add .
git commit -m "根据讨论修改用户画像"
git push
```

### 3.6 开 Pull Request

1. 打开 GitHub 仓库页
2. 会看到「Compare & pull request」
3. 标题写清改了什么
4. 说明里写：改了哪些文件、请谁看
5. 目标分支选 `main`
6. 点 **Create pull request**

至少请一名组员看过再合并。不要自己改完立刻强行合并到 `main`，除非是组长约定的紧急小修复。

## 4. 和别人的改动保持同步

别人的 PR 已经合进 `main` 后，你还在自己的分支上工作时：

```bash
git checkout main
git pull origin main
git checkout feature/requirement-research
git merge main
```

如果出现冲突：

1. 打开提示冲突的文件
2. 搜索 `<<<<<<<`、`=======`、`>>>>>>>`
3. 和对方或组长确认该留哪一段
4. 删掉冲突标记，保存
5. 再执行：

```bash
git add .
git commit -m "合并 main 并解决冲突"
git push
```

## 5. 常用命令速查

| 命令                   | 作用                   |
| ---------------------- | ---------------------- |
| `git status`           | 看当前分支和未提交改动 |
| `git pull`             | 拉取远程更新           |
| `git add 文件`         | 把文件加入暂存区       |
| `git commit -m "说明"` | 生成本地提交           |
| `git push`             | 推到 GitHub            |
| `git log --oneline`    | 看最近提交             |
| `git checkout main`    | 切回主分支             |
| `git checkout 分支名`  | 切换到已有分支         |
| `git branch`           | 查看本地分支           |

## 6. 角色建议

| 角色           | 本机可以做                            | 注意                                                       |
| -------------- | ------------------------------------- | ---------------------------------------------------------- |
| 普通组员       | 克隆、建分支、提交、开 PR             | 不要直接改 `main`                                          |
| 组长 / Owner   | 合并 PR、管理权限、必要时回退错误提交 | 合并前先看 diff，详见 [组长协作指南.md](./组长协作指南.md) |
| 只写文档的同学 | 同样走分支和 PR                       | 不要把 Word 临时稿和一堆截图无说明地整包上传               |

文档、原型、代码都用同一套流程。只是改 Markdown，也请走分支，避免两个人同时大改同一份文件而互相覆盖。

## 7. 常见问题

**Q：`git clone` 失败，提示没有权限？**  
先确认已经接受组织邀请，仓库 Collaborators 里有你，权限至少是 Write。

**Q：`push` 被拒绝？**  
常见原因：你还在 `main` 上直接推，或远程已经有别人的新提交。先 `git pull`，或改到自己的功能分支再推。

**Q：我不小心在 `main` 上改了怎么办？**  
还没 commit：把改动拷走，`git checkout -- 文件名` 还原，再切到新分支重做。  
已经 commit 但还没 push：告诉组长，不要强行改公共历史。

**Q：中文文件名或提交说明乱码？**  
按本文「第一次配置」一节补上 `core.quotepath` 配置，提交说明尽量用简体中文完整句子。

**Q：可不可以只用 GitHub 网页改文件？**  
改一两处错别字可以。改项目书、多人同时写文档时，请在本机分支进行，减少互相覆盖。

## 8. 第一次建议这样试一遍

1. 克隆仓库
2. 执行 `git checkout -b docs/hello`
3. 在任意说明文件末尾加一行自己的名字（或单独加 `TEAM.md`，由组长决定）
4. `git add` → `git commit` → `git push`
5. 在 GitHub 开一个 PR，请组长合并

走通这一次，后面写调研、画架构图、做原型都按同一套做即可。
